Audit qualité – microservices Java HTTP & Java Javalin
Date : 13 novembre 2025

Périmètre analysé
- Microservices "classiques" basés sur com.sun.net.httpserver (auth, catalog, order, user, gateway) sous apps/plant_shop_java/Structure_en_micro_services/plant_shop_java_microservices.
- Microservices Javalin (auth, catalog, order, user, gateway) sous apps/plant_shop_java/Structure_en_micro_services/plant_shop_java_javalin_microservices.
- Base de code utilitaire commune (utils, config, gateway).

Forces communes
- Modélisation métier relativement claire : usage des records pour Order/Plant/User côté HTTP et DTO mappeurs côté Javalin.
- Hashage BCrypt homogène et centralisé (util/PasswordUtil.java dans les deux variantes) limitant les failles évidentes autour des mots de passe.
- Gateway appliquant la propagation d’identité via en-têtes X-User-Id / X-User-Admin et protégeant les routes publiques vs privées.

Risques critiques
1. Authentification brisée côté order-service HTTP : AuthContext.userId() lève IllegalStateException quand l’utilisateur n’est pas connecté, mais handle() l’appelle avant tout contrôle (apps/.../order-service/src/controller/OrderController.java:117-135). Résultat : 500 systématiques au lieu d’un 401 et impossibilité d’utiliser l’API orders.
2. Sessions en mémoire locale pour tous les services (apps/.../auth-service/AuthService.java:163-257 et équivalent Javalin) : aucune persistance, rotation, TTL ni coordination inter-nœuds → déconnexion massive au moindre redémarrage, impossibilité de scaler horizontalement et surface d’attaque (vol de session non expirée).
3. Couplage direct à la même base PostgreSQL depuis tous les microservices (ex. apps/.../order-service/src/controller/OrderController.java:69-161 et PlantRepository embarqué) : pas de frontières CQRS, la moindre migration de schéma casse l’ensemble, et ordre-service peut effacer/altérer des données catalog sans passer par une API sécurisée.
4. Contrats d’API non respectés sur le gateway : GatewayConfig.port() lit SERVER_ADDRESS (ex. "http://localhost:4100") puis le parse en int (apps/.../gateway/src/Main.java:51-63). Un paramètre conforme ("http://...") déclenchera NumberFormatException et empêchera la gateway de démarrer.

Problèmes majeurs (court/moyen terme)
1. Répétition massive des BaseController par service (auth/catalog/order/users) côté HTTP (ex. apps/.../catalog-service/src/controller/PlantController.java et apps/.../user-service/src/controller/UserController.java). La logique de parsing JSON, sérialisation, gestion d’erreurs et CORS est dupliquée, difficile à corriger de façon cohérente et empêche l’introduction de middlewares (rate-limit, traces, métriques).
2. Transactions et rollback fragiles côté order-service Javalin : la méthode create() change auto-commit sur la Connection partagée (apps/.../javalin_microservices/order-service/src/controllers/OrderController.java:70-112). En multi-threads, un autre thread peut voir autoCommit=false et rester bloqué. De plus, les appels HTTP de décrément de stock ne sont pas intégrés dans la transaction (pas de sagas ni de rollback compensatoire).
3. ApplicationController Javalin (apps/.../javalin_microservices/catalog-service/src/controllers/ApplicationController.java:17-133) instancie Auth/Plant/User/Order controllers dans le même process, ce qui revient à exposer toutes les routes d’un monolithe sous chaque microservice. Cela annule l’isolation, multiplie les dépendances SQL et rend le déploiement indépendant impossible.
4. Validation de données superficielle : création/édition de plantes accepte price = NaN / négatif (PlantController côté HTTP et Javalin) et update stock via PATCH n’impose aucun minimum/maximum. Côté utilisateurs, aucun contrôle de force de mot de passe ni de format d’email, ni de limitation de tentatives de login.
5. Observabilité quasi inexistante : expose printf ou e.printStackTrace (ex. OrderController HTTP lignes 137-140, AuthService, gateway). Pas de journalisation structurée, métriques ni corrélation de requêtes – débogage en production quasi impossible.

Opportunités d’amélioration rapides
1. Extraire un module "http-core" (utilisation d’un framework léger type Javalin/Helidon) pour remplacer com.sun.* et mutualiser middlewares, parsing, gestion d’exceptions et auth.
2. Remplacer les HashMap de session par un provider partagé (JWT signé, Redis, Postgres) avec TTL configurable, rotation et révocation serveur.
3. Mettre chaque microservice derrière son propre schéma/bdd ou a minima des vues SQL en lecture seule pour éviter les écritures croisées.
4. Revoir le gateway config : séparer SERVER_HOST (string) et SERVER_PORT (int) avec validation au démarrage et messages d’erreur explicites.
5. Ajouter des tests d’intégration contractuels (ex. Newman/Postman ou RestAssured) ciblant les scénarios critiques : commande avec stock insuffisant, user non admin sur /admin, expiration de session.
6. Pour Javalin, déplacer ApplicationController vers un unique service API ou, si l’objectif est la pratique multi-langage, scinder réellement les modules (auth-service ne devrait pas embarquer OrderController, etc.).

Priorisation recommandée
- Immédiat : corriger AuthContext / OrderController, GatewayConfig, sécuriser les sessions et séparer les routes par service.
- 1-2 itérations : mettre en place migrations versionnées, transactions sûres (ou pattern outbox/saga) et tests automatisés.
- Moyen terme : investir dans une plateforme d’observabilité (logs structurés + traces), factoriser le code HTTP, clarifier la frontière entre les variantes (HTTP pur vs Javalin) pour éviter la dérive monolithique.
