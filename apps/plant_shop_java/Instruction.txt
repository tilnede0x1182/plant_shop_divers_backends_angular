• ### Logique fonctionnelle (texte uniquement) – Quarkus distribué

  - Principe général : on décompose le monolithe Quarkus existant en quatre services métiers (auth, catalog, order, user) + une gateway HTTP unique. Chaque service reste dans le même process JVM que les
    autres (architecture “distribuée” non autonome) : ils partagent config/.env, la même base PostgreSQL et les utilitaires communs (mappers, gestion des identités transférées, accès DB).
  - Auth-service
      - Routes POST /api/auth/login, POST /api/auth/register, POST /api/auth/logout, GET /api/auth/me, GET /api/auth/_session.
      - Stocke les utilisateurs (users), hash BCrypt.
      - Gère les sessions en mémoire (UUID → userId) + cookie SameSite=Lax.
      - Expose l’identité courante à la gateway via _session.
  - Catalog-service
      - Routes publiques GET /api/plants, GET /api/plants/{id} ; routes admin POST/PATCH/DELETE /api/admin/plants, plus endpoint interne PATCH /api/internal/plants/{id}/stock.
      - Persiste les plantes (plants), applique validation de stock/prix.
      - N’autorise les mutations que si le header X-User-Admin=true.
  - Order-service
      - Routes GET /api/orders, POST /api/orders, PATCH /api/orders/{id} (admin), DELETE /api/orders/{id} (admin).
      - Lors de la création d’une commande : vérification du stock via catalog-service (appel HTTP interne via gateway), décrémentation du stock, persistance orders + order_items.
      - Lors de la sérialisation vers le front, on filtre les items dont la plante a été supprimée (évite les 500 sur l’Order Index).
  - User-service
      - Routes admin GET /api/admin/users, POST /api/users, PATCH /api/users/{id}, DELETE /api/users/{id} + routes user GET/PUT /api/users/{id} (propre compte).
      - Gère les rôles (isAdmin).
      - Requiert X-User-* pour déterminer les droits.
  - Gateway
      - Reverse proxy HTTP sur http://localhost:4100/api/*.
      - Routes publiques : GET /plants* ; toutes les autres nécessitent une session valable (validation via _session).
      - Propage l’identité via headers X-User-Id / X-User-Admin.
      - Garantit que les cookies de session sont relayés.

  ### Logique fonctionnelle – Quarkus microservices

  - Principe général : même découpage fonctionnel que ci-dessus, mais cette fois chaque service est autonome (projet Quarkus Maven indépendant). Chaque microservice possède son application.properties,
    son mvnw, ses dépendances Quarkus, et s’exécute sur son propre port (auth 6101, catalog 6102, order 6103, user 6104, gateway 4100). Partage de la base PostgreSQL mais configuration injectée
    par .env.
  - Auth-service (Quarkus)
      - RESTEasy ressources AuthResource, SessionResource.
      - Beans CDI pour SessionStore, PasswordService.
      - Sécurité gérée avec quarkus-security (form auth custom) + ContainerRequestFilter pour peupler SecurityIdentity.
      - Tests Quarkus (@QuarkusTest) pour login/register.
  - Catalog-service
      - RESTEasy + Panache : PlantEntity, PlantRepository, PlantResource.
      - Validation via Bean Validation.
      - CORS activé pour http://localhost:8300.
      - Endpoints identiques à la version distribuée mais service réellement autonome.
  - Order-service
      - RESTEasy OrderResource, AdminOrderResource.
      - Appels vers catalog via REST Client Quarkus (@RegisterRestClient).
      - Transaction Panache sur OrderEntity, OrderItemEntity.
      - Filtre ForwardedIdentityFilter CDI pour récupérer X-User-*.
  - User-service
      - REST resources pour CRUD admin + self update.
      - Vérifications des rôles via @RolesAllowed ou filtre custom.
      - Réutilisation d’un module commun (DTO + mappers) packagé en jar partagé.
  - Gateway
      - Peut rester en Java/PM2 ou devenir un module Quarkus “proxy” (RESTEasy/Vert.x).
      - Dans la version microservices, il tourne indépendamment, effectue les mêmes vérifications (session → headers) et redirige vers http://localhost:{servicePort}/api/....

  Ces descriptions textuelles couvrent la logique attendue pour les deux variantes Quarkus en suivant vos conventions (distribué = monolithe découpé / microservices = services autonomes).
