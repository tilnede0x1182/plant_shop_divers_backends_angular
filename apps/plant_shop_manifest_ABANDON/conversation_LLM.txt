  - In Android’s Vendor Interface (VINTF), the framework manifest is the counterpart to the device/vendor manifests and lists the HALs served by modules on the system, product, or system_ext partitions;
    it’s typically stored under /system/libhidl/manifest.xml for the core system portion provided by Google. (source.android.com (https://source.android.com/docs/core/architecture/vintf/objects?
    utm_source=openai))
  - A complete framework manifest is composed of three fragments—system, product, and system_ext—allowing OEMs to declare services shipped outside the vendor/ODM partitions without modifying Google’s
    system manifest. (source.android.com (https://source.android.com/docs/core/architecture/vintf/objects?utm_source=openai))
  - Each fragment uses the shared VINTF XML schema (<manifest version="…", type="framework">) to describe HAL names, transport (for example hwbinder), interface versions (fqname), and other metadata,
    ensuring compatibility checks against the framework compatibility matrix (FCM). (source.android.com (https://source.android.com/docs/core/architecture/vintf/objects?utm_source=openai))
  - You can split declarations across multiple XML files (“manifest fragments”) and package them inside the relevant APEX modules (prebuilt_etc) so that HAL updates remain tied to the modules that ship
    them. (source.android.com (https://source.android.com/docs/core/architecture/vintf/objects?utm_source=openai))
  - When a HAL implementation moves between partitions—say from vendor to system_ext—its manifest type must switch from device to framework, otherwise VINTF compatibility validation fails during
    assembly (assemble_vintf) or on-device checks. (source.android.com (https://source.android.com/docs/core/architecture/vintf/objects?utm_source=openai))

• Dans Manifest, le troisième argument que reçoivent tes handlers (manifest dans tes fichiers) n’est qu’une instance de BackendSDK. Chaque appel manifest.from('users')… repasse donc par CrudService.
  Regarde apps/plant_shop_manifest_ABANDON/node_modules/manifest/dist/manifest/src/crud/services/crud.service.js:270-282 : la méthode getVisibleProps retire systématiquement toute propriété nommée
  password, puis enlève aussi les props marquées hidden. Comme password fait partie des AUTHENTICABLE_PROPS et est déclaré hidden dans node_modules/manifest/dist/manifest/src/constants.js:24-45, aucun
  handler ne peut récupérer le hash via l’SDK, même avec fullVersion. C’est pour ça que ton authLogin obtient user.password === undefined.

  Pour autoriser un handler à voir le hash (par exemple pour comparer un login), tu as trois options :

  1. Utiliser directement le service d’auth Manifest : au lieu d’essayer de lire la colonne via l’SDK, injecte AuthService (ou expose-le depuis HandlerService) et appelle sa méthode
     findUserFromCredentials. C’est ce que fait Manifest en interne (node_modules/manifest/dist/manifest/src/auth/auth.service.js:66-150) pour vérifier les identifiants sans jamais rendre le hash au
     client.
     CrudService filtre le champ.
  3. Modifier CrudService (à tes risques) : retirer ou conditionner le filter((prop) => prop.name !== 'password') dans getVisibleProps. Ça réintroduira le champ dans toutes les réponses SDK, donc il
     faudra absolument filtrer côté handler avant de répondre pour ne jamais renvoyer le hash au frontend.

  En résumé, tant que tu t’appuies sur l’SDK exposé aux handlers, Manifest masque password par design. Il faut soit passer par AuthService, soit personnaliser la lib (en sachant que c’est du code généré
  dans node_modules).


› " Il faut soit passer par AuthService" expliquez


• Le service Nest AuthService de Manifest (apps/plant_shop_manifest_ABANDON/node_modules/manifest/dist/manifest/src/auth/auth.service.js:1) contourne justement le filtrage des mots de passe :

  - Sa méthode findUserFromCredentials(entitySlug, email, password) récupère directement le repository TypeORM (entityService.getEntityRepository) pour lire l’entité complète, compare le mot de passe
    avec bcrypt, puis renvoie l’objet complet si c’est OK (auth.service.js:128-149). Ce chemin n’utilise pas le BackendSDK, donc il n’applique pas getVisibleProps qui supprimait les champs sensibles.

  Pour en profiter dans un handler custom :

  1. Étendre HandlerService (même fichier, handler.service.js:14-64) pour injecter AuthService en plus de BackendSDK :

     constructor(configService, sdk, authService) { ... }
  2. Lorsqu’il appelle handlerFn, lui transmettre cette dépendance supplémentaire :

     return handlerFn(req, res, { sdk: this.sdk, auth: this.authService });
  3. Adapter tes handlers (handlers/auth/authLogin.js, etc.) pour accepter ce nouvel objet :

     module.exports = async (req, res, ctx) => {
       const user = await ctx.auth.findUserFromCredentials('users', email, password);
       ...
     };
     Tu n’utilises plus ctx.sdk.from('users') pour lire le mot de passe, donc aucune censure.

  Sinon, si tu veux éviter de modifier HandlerService, tu peux directement require le AuthService Nest en créant une instance du module Manifest, mais c’est plus lourd. Ajuster HandlerService reste la
  voie la plus simple : il est déjà dans ton projet, et c’est lui qui décide de ce que les handlers reçoivent.

› BIGSERIAL jamais entedu parler


• BIGSERIAL est un mot-clé PostgreSQL qui crée automatiquement une colonne entière auto-incrémentée sur 64 bits. Il équivaut à :

  true_id BIGINT
      DEFAULT nextval('true_id_seq')

  plus la création de la séquence true_id_seq liée à la colonne. En bref :

  - SERIAL → entier 32 bits auto-incrémenté.
  - BIGSERIAL → entier 64 bits auto-incrémenté (plus sûr si tu veux dépasser ~2 milliards).
  - SMALLSERIAL → entier 16 bits.

  Tu peux l’utiliser directement dans ta définition de table :

  CREATE TABLE "user" (
    id UUID PRIMARY KEY,
    true_id BIGSERIAL UNIQUE NOT NULL,
    ...
  );

  ou via un ALTER TABLE ... ADD COLUMN true_id BIGSERIAL. Chaque insertion qui ne précise pas true_id récupérera automatiquement la prochaine valeur de la séquence, sans que tu aies à t’occuper de la
  logique d’auto-incrément.

• Manifest reconstruit la base à chaque démarrage en lisant manifest.yml. Le service TypeORM du framework démarre systématiquement avec synchronize = true, ce qui supprime ou recrée les colonnes/
  relations pour coller exactement au schéma décrit dans le manifest. Il n’existe pas (à date) d’option de configuration pour désactiver cette synchronisation automatique : la stack est volontairement
  opinée pour garantir que la base reflète en permanence le fichier Manifest.

  - Modifier migrate.sql ne suffit pas, et patcher les fichiers node_modules est fragile : une réinstallation écrase les changements.

  En résumé, il n’y a pas de paramètre côté Manifest pour couper l’auto-synchronisation. La solution viable consiste à reprocher vos colonnes/index personnalisés après chaque reset/seed via un script
